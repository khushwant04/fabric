# ADR 0008: Use Account-Scoped Tenancy and Stamp Credentials

**Decision status:** Accepted  
**Implementation status:** Partially implemented — the control-plane half (account-scoped tenancy, credential classes, enrollment, placement authorization, revocation) ships in [`control-plane/`](../../../control-plane/); the cluster agent, operator, and telemetry ingestion do not exist yet.  
**Date:** 2026-08-11

## Context

Fabric needs one simple customer ownership boundary for the first release and a secure way to associate BYOI hardware, deployments, status, and telemetry with the correct customer. Reusing human/API credentials inside Kubernetes would increase credential exposure and confuse user, inference, and machine authorization. Shared managed infrastructure also cannot truthfully belong to a single customer account.

## Decision

Account is the only customer hierarchy level for MVP. There are no organization, workspace, project, or environment containers. Every tenant-owned product resource carries authoritative `account_id`. Auth0 users are global authentication identities; account access is represented by account-scoped memberships.

Use a protected internal Fabric system account to own managed-serverless stamps. Customer BYOI stamps belong to the enrolling customer account. Customer deployments and placements always belong to the customer account, including placements onto system-account managed stamps.

Credential classes are separate and non-interchangeable:

- Auth0 access token proves human identity to the token endpoint.
- Fabric API key exchanges for a short-lived control or inference JWT according to account-owned key scopes.
- Fabric control JWT authorizes account-scoped product APIs.
- Fabric inference JWT authorizes direct deployment invocation.
- One-time account-bound enrollment token registers a new stamp.
- Revocable agent credential authorizes heartbeat, bounded capabilities, desired-state reads, and status writes only.
- Separate write-only telemetry credential authorizes collector export in every environment, including testing.

During enrollment, the server derives `account_id` from the enrollment record and ignores caller-supplied ownership. The agent stores its credential in an agent-only Kubernetes Secret, while the collector receives a distinct write-only telemetry credential in a collector-only Secret.

Usage ingestion now enforces this: the telemetry credential is the only credential accepted there, ownership is resolved from that credential and the placement rather than the payload, and a stamp reporting for a deployment it does not serve is rejected. Tests cover the agent credential and a control token both being refused. The operator receives only Kubernetes RBAC and no central account/API credential.

Placement authorization requires customer ownership of the deployment/placement, same-account ownership for BYOI stamps, or explicit eligibility for a managed stamp owned by the Fabric system account.

Reserved Kubernetes account/stamp/deployment metadata is generated by the agent/operator and is not authoritative when supplied by customers. Central telemetry ingestion resolves ownership from the authenticated stamp/telemetry credential, validates deployment placement, and overwrites untrusted ownership attributes.

## Consequences

### Positive

- One tenant key (`account_id`) simplifies APIs, database integrity, JWTs, audit, placement, and telemetry.
- No long-lived human or inference API key is stored in a customer cluster.
- Stamp compromise is scoped to one stamp/account and machine operations.
- Managed shared capacity has an honest platform owner while customer placements remain customer-owned.
- Composite account-aware foreign keys and optional RLS can defend against cross-account application bugs.

### Negative

- Users requiring multiple accounts need explicit memberships and account selection during token exchange.
- Managed placement crosses customer deployment ownership and system-account infrastructure ownership, requiring explicit authorization logic.
- Multiple credential lifecycles, scopes, revocation, and rotation must be implemented and tested.
- Cross-account BYOI sharing is not supported in MVP.

## Alternatives considered

- **Organization/workspace/project hierarchy:** rejected for MVP because it adds authorization and migration complexity before a demonstrated need.
- **Customer API key stored in the agent/operator:** rejected because it grants broad user authority to a long-running cluster component.
- **Caller supplies account ID during enrollment:** rejected because it permits ownership spoofing unless account identity is derived from a verified token record.
- **Managed stamp belongs to the deploying customer:** rejected because managed capacity may be shared and reallocated across customers.
- **Trust Kubernetes or telemetry labels for ownership:** rejected because customer-controlled labels are spoofable.
- **One credential for control, inference, stamp, and telemetry:** rejected due to excessive blast radius and confused audiences.

## Verification

Acceptance tests must demonstrate:

- Every tenant resource and relationship is account scoped.
- Composite tenant constraints reject cross-account references.
- Auth0 exchange returns `account_membership_required` with no token for zero active memberships, may implicitly select exactly one, requires valid selection for multiple or returns `account_selection_required` with no token, rejects foreign/inactive selections, and issues one account-bound JWT on success; API-key exchange ignores account selectors and derives account/scopes from the key record.
- An API key never carries a control scope the creating principal lacks.
- Enrollment ignores spoofed account fields and derives ownership from the one-time token, and a token cannot be claimed twice even concurrently.
- BYOI placement rejects a stamp owned by another customer account.
- Managed placement requires a system-account managed stamp, a supported distribution, and account entitlement.
- Managed status writes resolve the owning account from the placement, so shared capacity can report status for a customer deployment without the customer account owning the stamp.
- Agent credentials cannot invoke telemetry, general control APIs, or inference; telemetry credentials cannot read desired state, write status, or invoke control/inference APIs.
- Operator pods have no central stamp/API credential.
- Reserved Kubernetes ownership metadata cannot be overridden by customer input.
- Central telemetry rejects wrong-stamp/deployment ownership and overwrites untrusted account labels.
- Revoked or expired enrollment, agent, and telemetry credentials are denied independently, and revoking a stamp stops all further synchronization.

Covered by the control-plane suite today: account scoping, composite constraints,
Auth0 and API-key exchange branches, scope delegation limits, enrollment ownership
and concurrent single use, BYOI and managed placement authorization including the
distribution gate, placement-derived status ownership, credential-class separation
in both directions, and stamp/credential/enrollment-token revocation.

Not yet verifiable because the components do not exist: operator credential
absence, reserved Kubernetes metadata handling, and central telemetry ownership
enforcement.
